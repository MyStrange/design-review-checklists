# Чек-листы дизайн-ревью

Автоматически забирает с Яндекс-почты конспекты встреч дизайн-ревью,
превращает их в чек-листы (через бесплатный LLM API) и публикует на
веб-страницу с навигацией **Дизайнер → Дата → Проект → пункты с галочками**.

Работает сам, бесплатно и **не зависит от чьей-либо подписки** на ChatGPT/Claude:
движок — GitHub Actions, модель — бесплатный Gemini API (один проектный ключ).

- **Живой сайт (его видят дизайнеры):** https://design-review-checklists-git-main-shsbs.vercel.app
- **Репозиторий (источник правды):** `github.com/MyStrange/design-review-checklists` (приватный)

## ⚠️ Как с этим работать (важно для нового чата с ИИ-ассистентом)

**Всё живёт в GitHub, а не на компьютере.** Локальная папка — лишь рабочая копия,
и она почти всегда отстаёт: свежие данные (новые встречи) автоматика заливает
прямо в репозиторий. Поэтому:

1. **Не диагностируй по локальным файлам** — они устаревшие. Сначала `git pull`,
   и только потом смотри `data/checklists.json` и `docs/`.
2. **Доступ уже настроен:** SSH-ключ владельца привязан к GitHub (`MyStrange`),
   `origin` использует SSH. Можно сразу `git pull` и `git push` в `main`.
3. **Деплой автоматический:** репозиторий связан с **Vercel** — после `git push`
   в `main` сайт сам пересобирается за 1–2 минуты. Ничего вручную деплоить не надо.
4. **Бот сам себя обновляет:** GitHub Actions по вт/чт забирает письмо, разбирает
   и коммитит новые данные + пересобранный сайт. Эти коммиты прилетают в `main`.

### Чтобы поправить сайт/код и выкатить:

```bash
git pull --ff-only origin main          # 1. подтянуть свежее (ОБЯЗАТЕЛЬНО)
# 2. ... внести правки в src/ ...
python -m src.main --build-only         # 3. пересобрать docs/index.html из данных
git add -A && git commit -m "что сделал"
git push origin main                    # 4. Vercel сам выкатит за пару минут
```

## Как это устроено

```
Яндекс-почта (IMAP)
   │  по вт/чт прогон стартует к концу встречи и сам ждёт письмо 5 часов
   │  (+ ежедневный проход в 06:10 и 09:10 МСК — подобрать, что приехало мимо)
   ▼
GitHub Actions  ──►  src/main.py
   ├─ fetch.py   найти письмо от keeper@telemost.yandex.ru с темой «Ревью Записи», скачать .txt
   ├─ llm.py     текст расшифровки → структурированный чек-лист (Gemini, бесплатно)
   ├─ build.py   data/checklists.json → docs/index.html
   └─ git commit + push
   ▼
Vercel (привязан к main) сам пересобирает и отдаёт docs/index.html
```

- Письмо распознаётся по отправителю **и** теме; дата берётся из темы (`от 02.06.2026`).
- `ч.1` = ревью по вторникам, `ч.2` = по четвергам — это **разные встречи**, не склеиваются.
- Обработанные письма запоминаются по UID в `data/checklists.json` — повторно не обрабатываются.
- Галочки в пунктах хранятся в браузере пользователя, у каждого свои. Пишем их
  сразу в localStorage, sessionStorage и IndexedDB и читаем самую свежую копию:
  во встроенном браузере Телеграма и в приватном режиме localStorage может быть
  запрещён или вычищен, и одной копии не хватает.
- Новые встречи разбираются и анонсируются по возрастанию даты, а строка про
  смену короны считается вокруг каждой встречи отдельно — иначе, когда за один
  прогон приезжают две встречи, корона достаётся не той.
- Пуши уходят только в будни с 10:00 до 18:00 МСК. Всё, что разобрано в выходной,
  ночью или вечером, кладётся в очередь (`pending_notifications` в данных) и уходит
  в следующее рабочее окно — очередь разбирает любой прогон, который в него попал.

### Надёжность: расписание GitHub — не расписание

Тут две независимые беды: непредсказуемое письмо и ненадёжный планировщик.

**Конспект приходит когда захочет.** По логам прошлых встреч:

| Встреча | Когда появился конспект |
|---|---|
| 29.10, чт | в пределах ~5 часов после встречи |
| 10.11, вт | в тот же вечер, до 02:40 МСК |
| 12.11, чт | ночью, между 02:44 и 04:29 МСК |
| 05.11, чт | позже 04:08 МСК **следующего** дня |

Поэтому «проверить через 15 минут после встречи» не работает, и подобрать точку
в расписании нельзя — её нет.

**Запланированные запуски** на бесплатном плане **опаздывают на 4–8 часов и
теряются**, а пропущенные события GitHub не копит. Замеры по этому репозиторию:

| Что просили | Что было на самом деле |
|---|---|
| вт/чт: 32 проверки каждые 15 минут | случалось 1–3, иногда ночью |
| ежедневно 07:05 UTC (`morning-send`) | приезжало в 14:00–17:20 UTC |

Отсюда два следствия, из-за которых чек-листы терялись и наслаивались:

1. Прогон приезжал, когда письма ещё (или уже) не видел, и конспект подхватывал
   только прогон следующего дня ревью — 10 ноября в 02:44 МСК так ушли сразу два
   чек-листа, за 5 и за 10 ноября.
2. Одна ошибка модели (`503 high demand` 12 ноября) валила весь прогон, и шаг
   коммита уже не выполнялся — работа прогона пропадала целиком.

Что с этим сделано:

- **Ждёт письмо сам прогон, а не планировщик.** `--watch МИНУТ` перепроверяет
  почту каждые 10 минут (в дни ревью — 4 часа подряд) и заканчивает сразу, как
  разобрал встречу. Поэтому точек в `cron` мало: частая сетка надёжности не даёт.
- **Ежедневный проход** (06:10 и 09:10 МСК): подбирает всё, что приехало мимо
  окна ожидания — ночью, в выходной, или пока прогон дня ревью падал. Письмо
  никуда не девается: оно лежит в ящике 45 дней, а разобранные помечены по UID.
  Худший случай — чек-лист появится на сайте утром следующего дня, а пуш уйдёт в
  ближайшее рабочее окно. Без этого встречи наслаивались: 10 ноября в 02:44 МСК
  ушли сразу два чек-листа, за 5 и за 10 ноября. Проход ежедневный, а не по
  будням, намеренно: разобрать и опубликовать можно и в субботу, а пуш всё равно
  дождётся понедельника.
- **Время прихода письма пишется в лог и в данные** (поле `received` у встречи):
  через несколько встреч будет видно реальное распределение, и расписание можно
  будет подкрутить по факту, а не на ощупь.
- **Падение не уносит работу.** Письмо, которое не разобралось, остаётся новым и
  ждёт следующего прохода; остальные встречи сохраняются и публикуются. Шаг
  коммита в workflow стоит с `if: always()`.
- **Модель перегружена — ждём дольше и пробуем запасную.** Семь попыток с
  паузами до 3 минут (было четыре по 15–45 секунд), затем `GEMINI_MODEL_FALLBACK`
  (по умолчанию `gemini-2.0-flash`): у неё свой лимит и своя очередь.

### Теги пунктов (бейджики)

Тег отвечает на вопрос «к кому идти с этим пунктом»: `product`, `dev`,
`research`, `seo`, `legal`, `branding`. Седьмой тег — `ux`: обычная правка,
которую дизайнер делает сам. **У `ux` бейджика на странице нет намеренно** —
это почти каждый пункт, и подпись на всех строках только шумела бы.

Тег ставит нейросеть, но она склонна помечать всё подряд как `ux` — так с июня
2026 бейджики и пропали. Поэтому поверх неё работает `src/tagging.py`: если в
тексте пункта прямо сказано, к кому идти («уточнить у продакта», «согласовать
с брендингом», «провести исследование»), тег ставится правилом. Явно выбранный
нейросетью специалист правилами не перебивается.

Новый тег добавляется в четырёх местах: `TAGS` в `src/main.py`, `enum` и
описание в промпте `src/llm.py`, `tagLabel` и стиль `.tag.<имя>` в
`src/build.py`, при желании — правило в `src/tagging.py`.

Перетегировать уже разобранные встречи (тексты и `id` пунктов не меняются,
поэтому чужие галочки остаются на месте):

```bash
python -m src.main --retag --dry-run
```

```bash
python -m src.main --retag
```

### Имена дизайнеров

Нейросеть может выдать имя в любом формате — «Григорьева Анна Сергеевна»,
«Анна Григорьева», с отчеством и без. Чтобы один человек не превратился в
несколько «дизайнеров», `config.short_name()` сопоставляет имена по фамилии+имени,
игнорируя отчество и порядок слов (см. `src/config.py`). Список и сайдбар на
сайте строятся **из реальных данных** автоматически — ничего хардкодить не нужно.

**Новый дизайнер:** добавь его в `NAME_MAP` (полное ФИО → короткое имя) и, если
надо тегать в Телеграме, в `TELEGRAM_USERNAMES` (короткое имя → `@username`).

## Структура

```
src/config.py   настройки (всё из переменных окружения)
src/fetch.py    забор писем по IMAP
src/llm.py      обращение к LLM (Gemini; легко заменить провайдера)
src/build.py    генерация HTML
src/main.py     оркестрация + CLI
data/checklists.json   накопленные данные + список обработанных писем
docs/           готовая страница (index.html) — отсюда раздаётся хостинг
.github/workflows/sync.yml   расписание и автозапуск
samples/        пример расшифровки для локального теста
```

## Секреты (GitHub → Settings → Secrets and variables → Actions)

| Имя | Что это |
|---|---|
| `YANDEX_USER` | полный адрес ящика, напр. `name@company.ru` |
| `YANDEX_APP_PASSWORD` | пароль приложения Яндекса (не основной пароль!) |
| `GEMINI_API_KEY` | бесплатный ключ Google AI Studio |

Необязательные переменные (можно не задавать): `GEMINI_MODEL`,
`GEMINI_MODEL_FALLBACK`, `LLM_PROVIDER`, `REVIEW_SENDER`, `SUBJECT_MUST_CONTAIN`,
`SEARCH_SINCE_DAYS`, `SITE_TITLE`.

## Локальный запуск / тест

Зависимостей ставить не нужно — только Python 3.

```bash
# 1) Только пересобрать страницу из текущих данных (без почты и без ключа):
python -m src.main --build-only
#    → откроется docs/index.html

# 2) Прогнать пример расшифровки через LLM (нужен GEMINI_API_KEY):
export GEMINI_API_KEY=...        # ключ из Google AI Studio
python -m src.main --file samples/sample_transcript.txt --date 2026-06-02 --part ч.1

# 3) Полный прогон (почта → страница), нужны все три секрета:
export YANDEX_USER=name@company.ru
export YANDEX_APP_PASSWORD=...
export GEMINI_API_KEY=...
python -m src.main
```

## Хостинг страницы

Сейчас сайт хостится на **Vercel** и привязан к ветке `main`: любой `git push`
в `main` автоматически пересобирает и выкатывает страницу (см. `vercel.json` —
отдаётся статика из `docs/`). Адрес: https://design-review-checklists-git-main-shsbs.vercel.app

`docs/index.html` — обычная статика, поэтому при желании её можно отдавать и
откуда угодно (GitHub Pages, Cloudflare Pages — output-каталог `docs`). Страница
отдаётся с `noindex` и `robots.txt`, поэтому в поиск не попадает.
